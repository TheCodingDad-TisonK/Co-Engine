# The engine contract

What a game on Co Engine writes against, as of v0.1.4. One HTML page, one closure: the build script opens the closure, joins the engine's parts (`engine/NN-*.js`) in front of the game's (`src/NN-*.js`), and closes it. A game part may use any engine name at its top level once `CO.setup` has run, which the game's first part does.

## The two calls

**`CO.setup(cfg)`** in the game's first part. It reads the settings and the save slot, makes the renderer, the scene, the camera, the sun and the sky bounce, draws the base textures and the palette, binds the page, makes the player, then runs the `setup` hooks.

| cfg | default | what it is |
|---|---|---|
| `canvas` | `co-canvas` | the canvas element id (made if missing) |
| `save` | `co-game` | the save key prefix: `<prefix>-slot` holds the slot number, `<prefix>-slot<n>` the save, `<prefix>-settings` the settings; `?save=<name>` on the page opens `<prefix>-<name>` instead, a save of its own |
| `settingsKey`, `slots` | prefix-settings, 3 | |
| `settings` | | extra settings with their defaults, merged over the engine's (`sens, invertY, quality, sound, vol, fps, fov, film, bob`) |
| `game` | `{}` | the hook object, `CO.game` (section 3); `CO.boot(GAME)` merges more into it |
| `spawn` | `{x: 0, z: 0, yaw: 0}` | where the player stands at boot |
| `exposure, background, fog, fov, near, far` | 0.82, 0x8fb0d4, {70, 190}, SET.fov, 0.08, 260 | the renderer and the camera (`background: null` for none) |
| `env` | true | the reflection studio |
| `hemi` | `{sky, ground, intensity}` | the sky bounce |
| `sun` | `{color, intensity, box 70, near, far 230, mapSize 4096, target [0,0,-20]}` | the shadow-casting sun |
| `lightBudget` | 12 | how many point lights stay visible |
| `post` | true | the post pass (grade, vignette, grain) |
| `palette` | true | `false` skips the engine's textures, normal maps and materials: the game draws its own |
| `input` | true | `false` binds none of the engine's keys, mouse or pointer lock: the game has its own |
| `saveDebounce` | 0 | milliseconds: `save()` coalesces a burst of calls into one write; `saveNow()` writes at once |

**`CO.boot(GAME)`** in the game's last part. It loads the save, builds the world, applies the settings, bakes, fills the start screen, starts the frame loop and publishes the handle.

| GAME | what it is |
|---|---|
| `handle` | the window property the game publishes (`DEPOT`): `window.<handle> = { enter, bootSlot, version, engine, T }` |
| `version`, `versionGlobal` | the game's version, or the global `sync-version` writes (`GAME_VERSION`) |
| `freshState()` | the game's default `S` |
| `migrate(s, fresh, missing)` | its save migrations, run on a loaded save with the fresh state's missing top-level keys already filled in; `missing[key]` is true for each one that was, so an old save can be told from a new field |
| `afterLoad(loaded)` | repairs on `S` before the world is built |
| `buildWorld(loaded)` | the walls, the floors, the props (`buildProps()`), the people, the sky (`buildSky`) |
| `afterBuild(loaded)` | meshes for the saved things |
| `bake` | `false` skips the static bake |
| `startStats(loaded)`, `startNote(loaded)` | the start screen's chips (strings) and the line under them |
| `onEnter(loaded)` | after the start button |
| `tick(dt)` | the world, once a frame while running (not blocked, not in photo mode) |
| `weather` | `false` turns the weather state machine off (the game ticks `tickWeatherState` itself) |
| `autoplay` | `false` leaves the `<prefix>-autoplay` session flag to the game's own front menu |
| `editMode`, `photo`, `lighting`, `hudFields` | `false` switches that engine pass off: the game brings its own build mode, photo mode, light by the hour, or HUD fields |
| `render(dt)` | draws the frame itself; return true |
| `boxSolid(w, h, d, x, y, z, opts)` | takes a `box(..., { solid: true })` footprint into the game's own blockers |
| `present(dt)` | the game's own per-frame presentation, after the engine's |
| `menuCamera(dt)` | the camera behind the start screen (default: an orbit) |
| `hiddenTick(dt)` | what still ticks in a hidden tab beside `tick` and the doors |
| `step(dt)` | what `T.run` calls beside `tick`, for the tests |
| `T` | an object or a function returning one: what the game adds to the test handle |

Any other field of GAME is a hook (section 3).

## The frame

Each frame, in order: the menu camera until `enter`; then, when started and not blocked, `photoTick` or `GAME.tick(dt)`, the weather, `updatePlayer(dt)`, the autosave timer; `worldTime` advances; `lighting`, the light budget, the shadow timer, the sky, bursts, doors, screens, build mode, traffic; `GAME.present(dt)` and the `frame` hooks; the `animated` list; focus, prompt, HUD, cards, the dev link; the render; the FPS readout.

While `CO.paused` is true the frame only ticks the scene camera, the light budget and the shadows and renders; nothing in the world moves. `CO.stepOnce = true` lets exactly one full frame through. The editor's pause and step buttons set these.

## 3. Hooks on CO.game

All optional. Where a hook returns a value the engine uses it; where it returns true the engine treats the thing as handled.

**World**
- `floorY(x, z, y)`: the floor height; default 0. `insideWalk(x, z)`: walkable ground for the crew; default everywhere. `indoors(x, z)`: under a roof, for the rain's sound. `roofAt(x, z)`: the roof height over a point, for the rain and snow; default 0 (outdoors). `powered()`: the mains, for the lamps; default true. `shadowLive()`: something big is moving, redraw the shadow map every frame.
- `groundY(x, z)`: the floor a prop stands on. `wallPlanes()`: faces a wall prop can hang on, `[{a: 'x'|'z', v, n, z0, z1 | x0, x1}]`. `editClamp(pt, def)`: keep a carried prop inside the site; returns `{x, z}`. `canEdit()`: gates build mode. `editBlocked()`: F2 does nothing now.
- `resolveDef(id, def)`: rewrite a prop's default spot for the world as it stands. `propAllowed(id, def)`: whether a prop stands now. `propWhere(id)`: where a removed prop stood, in words. `propOpen(def)`: whether a catalogue item is for sale now. `catalogueGroups`: `[[cat, heading, note]]`.
- `navPass(x, z)`: a point outside the walkable ground a walker may still cross (a docked trailer). `doorOpeners()`: `[{x, z}]`, the people with keys that doors open for.

**Player and input**
- `playerOverride(dt)`: take the frame (a vehicle, a seat); return true. `speedMul()`: scales the walk. `stepSurface(x, z, y)`: the step sound's surface. `collides(x, z, opt)`: the game's own blockers. `skipDyn(d)`: a dynamic blocker to ignore now.
- `hitObjects()`: more meshes to look at (instanced meshes). `hitDef(hit)`: a `{prompt, use, alt}` for one of them. `hitPriority(hit, first)`: this hit wins over the nearer one. `focusOff()`: no focus now.
- `useOverride()`: E, before the focus. `useFallback()`: E with nothing focused. `putDown()`: G with nothing focused.
- `mouseLook(e, sx, iy)`: take the mouse. `key(e)`: take a key before the engine's own bindings (after F12, F3, F9, Esc, F2 and build mode). `escape()`: take Esc first. `wheel(dir, e)`: take the wheel. `scanToggle(on)`: the game's own overlay the engine closes. `blocked()`: more layers that block the world. `photoBlocked()`: no photo mode now. `promptHidden()`: hide the E prompt.

**Shell**
- `hud()`: fill the HUD fields (under the dirty throttle). `panel(kind, tab)`: `{title, tabs: [[id, label]], tab, body}`. `panelAct(act, arg)`: a `data-act` button; return true when taken. The engine takes `restore` and `buy` only on its own catalogue panel, so a game's shop may have a `buy` of its own. `menu(k, button)`: a `data-menu` the engine does not know. `menuLine()`: the pause menu's first line. `guideHtml()`, `statsHtml()`, `settingsHtml()`: extra rows (`data-set` names the engine does not know go to `setting(k, v)`). `saveLooksRight(s)`: before an import.
- `devState()`: extra readout fields. `commands`: `{name: function (arg) { return 'what happened'; }}`.

## 4. Hooks on the bus

`hook(name, fn)` registers; the engine calls `runHooks(name, ...)`: `setup(cfg)`, `beforeBuild(loaded)`, `afterBuild(loaded)`, `boot(loaded)`, `enter(loaded)`, `frame(dt)`, `hud()`, `lighting(day, dawn, overcast, power)`, `sky(weather, dt)`, `weather(kind, prev)`, `settings(SET)`, `menuOpen()`, `panelAct(act, arg)`, `photo(on)`, `propCtx(ctx, g, id)`, `propBuilt(id, inst, def)`, `propRemoved(id, inst)`, `propPlaced(id, inst, def)`, `propDeleted(id, def)`, `editBought(c, def)`, `lockAll(lock)`, `humanMade(g, opt)`.

## 5. The page

The engine reads these elements when they exist and does nothing when they do not: `dc-start`, `dc-start-btn`, `dc-start-stats`, `dc-start-note`; `dc-hud` with `h-prompt`, `h-toasts`, `h-feed`, `h-fps`, `h-devlink`, `h-edit`, `h-day`, `h-clock`, `h-cash`; `dc-panel` with `dc-panel-title`, `dc-panel-tabs`, `dc-panel-body`, `dc-panel-close`; `dc-menu` with `.dc-menu-btns`, `dc-menu-body`, `dc-menu-sub`, `dc-m-devlink` and buttons carrying `data-menu` (`resume, back, edit, devlink, settings, guide, stats, saves, download, import, reset, quit`, else the game's); any card element named in `showCard`.

## 6. The prop definition

`defProp(id, def)`: `label, x, z, rot, y, cat, wall, fixed, extra, price, ico, desc, lvl, noBlob, quietPlace, when(), snap(def, pt, selfId), build(ctx, P, inst), after(ctx, P, inst)`. The ctx: `box, cyl, sphere, plane, sign, hit, solid, light, dynGroup, add, group, obstacles, id`, plus what the `propCtx` hooks add.

A prop's height (`h`, set in the inspector, by PageUp and PageDown, or by Drop) lifts the whole prop since 0.6.0; a definition that places its own parts by `P.h` (Depot Co.'s belt pieces) says `ownHeight: true`. Where a prop stands comes from three layers, each over the last: the definition's `x, z, rot`; the **shipped layout** (0.1.8), `CO.layout({ props: { id: { x, z, rot, h, hidden } }, placed: [{ id, type, x, z, rot, h }] })`, which the editor writes into `src/00-layout.js` (the first part in the build, so the boot sees it) whenever something is moved, hidden or placed in it; and the player's save, `S.layout[id] = {x, z, rot, h, hidden}`. `placed` entries are copies of a definition that ship with the game, built like props under their own ids; a player's own bought copies live in `S.custom = [{id, type, x, z, rot, h}]`. `propPlacement(id)` resolves the three layers, `propDefault(id)` the shipped place without the save. The editor's bridge reports the file to write with `layout()` (`props`, `placed`, `changed`, `copies`, `pending`, `code`) and takes the written one as the new baseline with `layoutAdopt(L)`: the copies it carries leave the editor's save and the save's overrides equal to the baseline go, so `pending` reads 0 until the next change.

## 6b. The terrain (0.2.0)

`CO.terrain({ w, d, cell, x0, z0, heights, paint, palette, maxH })` makes the ground a heightmap: `w` by `d` cells of `cell` metres from `x0, z0`, `heights` as `(w + 1) * (d + 1)` corner values row by row, `paint` as `w * d` indices into `palette` (`grass, dirt, gravel, sand, road, snow, water` by default; `CO.terrainPaint(name, { base, dots, n, r })` adds one). The editor writes it into `src/00-terrain.js`, which runs before the boot; `terrainBuild()` makes the mesh (one `BufferGeometry` under a painted canvas, out of the bake) when the world builds. `terrainY(x, z)` is the ground height (bilinear; 0 off the terrain) and the engine's `floorY` and `propGroundY` take the higher of the game's floor and the terrain, so the player and the props follow the ground. `terrainBrush(x, z, mode, radius, strength, tex)` raises, lowers, smooths or flattens the corners within the radius with a soft falloff, or paints the cells; the `road` mode (0.4.0) flattens the strip to the height under the brush and paints it road in one stroke. Where two paints meet, each cell's neighbours feather in over its edges, so the seam is soft; `terrainScatter(type, count, onPaint, seed)` places copies of a definition on the cells painted with one name, through the shipped layout. In the editor the Terrain tab makes one and the left button sculpts and paints it in Scene mode.

## 6c. Materials from a layer graph (0.2.0)

`CO.material(name, graph)` paints a texture from a stack of layers and registers it as `MAT[name]`, so a build function can say `MAT.myBrick`. A graph is `{ size, repeat: [rx, ry], layers: [{ type, color, color2, alpha, blend, n, size, size2, gap, angle, dark, vary }], roughness: 0.9 or { base, amp }, metalness, bump: { amp, strength } or null, emissive, emissiveIntensity, glow, opacity }`; the layer types are `fill, grain, blotches, cracks, noise, bricks, planks, tiles, stripes, checks, rings, speckle`, the blends the canvas's. Calling it again for the same name updates the same material in place, so every mesh on it follows. A graph's `glsl` (0.5.0) is a GLSL snippet run after the colour map: it may change `diffuseColor`, with `vUv` and `uTime` in seconds. The editor writes `src/00-materials.js`; its Materials tab edits the stack with a picture (`matShot`) beside it.

## 6d. Packs (0.2.0)

A pack is a folder `packs/<name>/` in the engine with `pack.js` (a part: `defProp` calls and their helpers, built from the engine's kit alone) and `pack.json` (title, description). The editor's Assets tab lists the packs and copies one into a game as `src/00-pack-<name>.js`; the game then places the props from Assets and ships what it placed through the layout. Pack props are `extra: true, shop: false`: placeable in the editor, not sold by the catalogue. `growco` (0.6.0) carries every prop of Grow Co. (61 props and six counter and wall fixtures: the till, the tip jar, the cards, the desk bell, the key hook, the staff roster) with the Grow helpers, materials and textures they are drawn with, inside one function scope so nothing clashes with the host; Grow's shop systems are stand-ins and a sandboxed fresh Grow save answers what the props read. A pack part placed ahead of `CO.setup` waits for the `beforeBuild` hook. The pack is generated from Grow Co.'s `src/`; `pack.json` lists its props for the editor. `depotco` (0.7.0) carries 131 props of Depot Co. (a four-bay rack row, belt pieces and the packing line, the moulder, palletiser, hopper, silo and dock loaders, the baler and wrapper, consoles and boards, lockers, break room and office furniture, signs, posters, floor paint and the yard) and `garageco` (0.7.0) the lock-up's 11. Both come from `tools/packs/make-pack.js <name>`, which walks every `defProp` in the game back to the helpers it uses (`game-extract.js`) and seals them in one function with a sandboxed save of that game (`game-pack-gen.js`, set up by `tools/packs/<name>.json`: the save, the names to carry, the props left out). A pack prop's uses say what it is; the game logic behind them stays in the game. Left out on purpose: props a whole hall long (the 68 m rack rows, the gantries, the mezzanine, the halls themselves), belts that need the depot's belt registry, Garage's roll door panel, and copies that only differ by hall. `basics` carries a control panel with a touch screen that opens and closes the gates, a sliding gate and a boom barrier (use them by hand or from the panel; their state lives in `S.pack`), a lever, signs, a crate, a pallet, a bench, a bin, a cone, a lamp post, a fence section and a planter.

**The 0.10.0 packs.** Thirteen packs for any game: `buildings`, `cars`, `city`, `nature`, `industrial`, `farm`, `park`, `home`, `office`, `shop`, `harbour`, `camping` and `roads`, 189 props. Each pack keeps its helpers behind a two-letter prefix (`bd`, `vh`, `ct`, `nt`, `in`, `fm`, `pl`, `hm`, `of`, `sh`, `hb`, `cp`, `rd`) because every pack shares one closure. A prop with moving parts (pedestrians, a campfire) puts them in `c.dynGroup()` so the static bake leaves them free to move; a light that glows uses `glowMat` and `lampMeshes`, as the engine lamps do. The road pieces are 7 m of tarmac between 2 m pavements, run along x, and are not solid: a 10 m straight set 10 m on from another meets it, the crossroads and T-junction are 11 m square, and the bend turns on a 10 m centre radius.

## 6e. Clips: animation as data (0.2.1)

`CO.clip(name, { duration, loop, tracks: [{ path, keys: [[t, value, ease]] }], events: [[t, name]] })` registers a clip; `playClip(obj, name, { loop, speed, blend, hold, onDone })` plays it on an object and `stopClip(obj)` stops it; the engine drives the playing list every frame (`clipTick` on the animated list, after the game's own passes, so a clip's keys win over the people rig's limb motion while it plays). A path names a node and a field: `rotation.x`, `position.y`, `scale.z`, `visible`, `opacity`, and since 0.5.0 `material.opacity`, `material.emissiveIntensity`, `material.color.r` and the like on the object, `child.2.rotation.y` its third child, `name.lamp.rotation.z` a named descendant, and on a person `leg.0`, `knee.1`, `arm.0`, `elbow.1`, `torso`, `head` with their fields. Ease is `smooth` (default), `linear`, `in`, `out` or `step`; `blend` eases in from the pose the object had; an event fires `runHooks('clipEvent', obj, name, play)`. The built-in clips are `wave, nod, cheer, point, lift` for a person and `spin, bob, swing, blink` for a prop. The editor's Animation tab plays, scrubs and keys a clip on the selected object (`clipKeyPose` writes the current pose into every track at a time) and writes the game's own clips to `src/00-clips.js`.

## 6f. UI as data (0.2.1)

`CO.ui({ hud: [{ label, value, color }], panels: { kind: { title, text, buttons: [{ label, action, primary, close }] } }, start: [expr], menuLine: expr, guide: text })` describes HUD chips (a row of their own under the engine's), panels (`openPanel(kind)` shows one: paragraphs and `- ` lists from the text, buttons that run a dev command such as `cash 100` or an expression), the start screen's chips, the pause menu's line and the guide, without code. Every value is an expression over the kit (`S.day`, `money(S.bank)`, `fmtTime(S.time)`). The game's own `GAME.hud`, `GAME.panel`, `GAME.startStats`, `GAME.menuLine` and `GAME.guideHtml` still win where they exist. The editor's UI tab edits it and writes `src/00-ui.js`.

## 6g. The prop modeller (0.3.0)

A model is a list of parts as data: `{ parts: [{ kind, mat, x, y, z, ry, name, ... }], autoSolid }` with, by kind, `box { w, h, d, r }` (`r` bevels the edges), `cyl { r, h, seg, rb }`, `sphere { r }`, `plane { w, h, rx }`, `sign { lines, w, h }`, `light { color, intensity, dist }`, `lathe { points: [[r, y]], seg }` (a profile revolved, 0.4.0), `extrude { shape: [[x, y]], depth }` (a flat shape pulled out, 0.4.0), `mesh { verts: [[x, y, z]], faces: [[a, b, c]] }` (0.5.0: in the Model tab a vertex drags with the left button), `solid { w, h, d }` (an obstacle, not drawn) and `hit { w, h, d, prompt }` (a use). `modelCode(model)` writes it out as a build function with the model kept in a `/*@model {...} */` comment at the top, each drawn part tagged `userData.part = i`, and with `autoSolid` an obstacle under every box and cylinder that touches the ground; `modelFrom(code)` reads it back, so a modelled prop round-trips through `src/`. `modelPreview(type, model)` is `preview` with the generated code, `modelStart(type)` turns a hand-written prop into a one-box model (Revert brings the code back until it is saved), `modelPick(type, nx, ny)` names the part under a viewport point, `modelMirror(model, axis)` flips it. The editor's Model tab edits the parts, adds, duplicates, mirrors and nudges them (arrows, PageUp and PageDown), picks a part by clicking it, and saves the code through the Pack flow.

**Parts from a prop drawn in code (0.8.0).** `modelConvert(type)` (the Model tab's Parts from this prop, the MCP tool `model_convert`) reads a placed copy of any prop back as a model and previews it: every box, cylinder, sphere and plane keeps its size, turn and lean (`rx`, `rz` on top of `ry`), a sign keeps its lines and options, a light its colour, a use box its prompt, an obstacle becomes a solid, and any other shape (a bent frond, a lathe, a skewed piece) becomes a `mesh` of its corners. Pieces the static bake merged away are read too; the contact shadow is left to the engine. A material the palette names keeps its name; one a pack carries keeps it by name (`"growco/MAT.wood"`, resolved by `packMat` through `CO.packMats`, each pack publishing its own); a picture drawn in code rides along as a PNG of at most 512 px (`img`); any other material keeps its colour, roughness, metalness, glow and opacity (`color`, `rough`, `metal`, `glow`, `opacity`). Every pack prop in the four packs converts and rebuilds at its own size.

**Saving a prop whose build is shared (0.8.0).** A pack's props all stand on one wrapper, and a builder can serve several props (Depot Co.'s TV and the shop TV). Saving over that shared code would reshape every one of them, so the editor (Model tab and Pack tab alike) writes such a prop as `modelOverride(type, build)` in `src/00-models.js`, one block per prop between `// model: <type>` and `// end model: <type>`. The engine lays the override on the prop whenever it is defined, before or after; delete a block to give the prop its shared build back.

## 6i. The world as things to edit (0.9.0)

Everything a game builds straight into its world is a **world item** the editor can select, move, turn, resize and remove, the way it handles props. A kit call (`lineWall`, `roomFloor`, `troffer`, `highBay`, `fenceRun`, `tree`, `lampPost`) builds into a group of its own, centred on what it built and standing on the ground, and the solids it adds travel with it. Any other mesh or group the build leaves at the top of the world is an item of its own (a plain box takes the solid laid on exactly its footprint). Props, people, doors, cars, lights, sprites, the terrain and the sky are not world items.

An item's key names what it is and where the game built it (`"lamp post@12.5,6"`, `"mesh plane 34x19.2@0,13.6"`), so it survives a reload and most changes to the game's code. What the editor changes is written to `src/00-world.js` as `CO.world({ key: { x, y, z, ry, sx, sy, sz, hidden } })`, only the fields that differ, and the boot lays it on the world after `afterBuild` and before the bake. A removed item is hidden, its solids are gone and it stays out of the bake; Put it back in the inspector, or deleting its line, gives the game's own version back.

**One world a stage (0.13.0).** A game that builds more than one world from the same code (Depot Co.'s six building stages, each its own page load) names the one a page builds in `GAME.worldVariant`, a string or a function (asked once the save is loaded, before the build, and again after it). Each named world keeps its own world edits, world copies and shipped layout, so what the editor changes at one stage stays at that stage. The editor writes every world into the same two files, a name after each list: `CO.world({ ... }, "stage 5")`, `CO.worldCopies([ ... ], "stage 5")` and `CO.layout({ ... }, "stage 5")`. Lists with no name belong to a game that names no world; a game that names worlds ignores them. The bridge's `worldVariant()` and the inspector's `worldItem.world` say which world the page is.

In the editor: click an item to select it; drag it in the scene camera (Ctrl and drag in the game view); Ctrl and the wheel turn it a quarter; the arrows nudge it, PageUp and PageDown lift it, R turns it; the inspector's scale fields resize it; Delete removes it. Undo covers all of it.

**Several at once.** Ctrl and a click adds a prop or a world item to the selection, or takes it away again; the last one picked is the one the inspector shows, gold, the others blue. Dragging any selected thing moves them all by the same step, the arrows nudge them all, Delete removes them all, and one undo puts a group move back. In the editor Ctrl no longer flies the scene camera down; C does. The bridge has `selection()`, `selectMany(ids)`, `moveSel(dx, dz)` and `removeSel()`.

**A box round many things (0.9.1).** Shift and a drag in the scene camera draw a selection box: every prop and world item whose footprint on the ground falls inside it is selected (Ctrl and Shift add to the selection). From the Top camera that is a building and everything in it in one go; then any of them drags them all.

**Duplicate, copy and paste (0.9.4).** Ctrl+D duplicates every selected prop and world item 1.5 m along and selects the copies; Ctrl+C copies the selection and Ctrl+V pastes it where the camera looks, keeping the arrangement; the inspector has a Duplicate button and Claude a `duplicate` tool. A prop copy is a placed copy the layout keeps. A world item's copy is a **world copy**: `CO.worldCopies([{ id, of, x, y, z, ry, sx, sy, sz }])` in `src/00-world.js`, built after the edits from the original's meshes (shared geometry and materials) with its solids cloned and laid where the copy stands. A copy is the original's look and solids: a door or a prompt stays with the original. Removing a copy takes it away; one undo takes a whole paste back. An item marked movesOnly is not copied.

**Doors and buildings (0.9.1).** A hinged door is a world item of its own (its frame and its leaf), or part of the item it is built in; its hinge's place, the solid it closes and its prompt follow wherever the item stands (`doorSync`). A game whose rules follow a building's place marks that item `userData.movesOnly = true`: the editor moves it but refuses to turn or resize it. Garage Co.'s lock-up is one such item, and its indoors, roof, walls, doorway and the customer's place at the desk read where it stands.

## 6h. Physics (0.3.0)

`body(obj, { mass, shape, size, restitution, friction, kinematic })` makes an object a rigid body: it falls under gravity, rests on the ground (`floorY`, so on the terrain too), on the engine's solids and on other bodies, slides with friction, bounces a little, and sleeps when still until something touches it. `removeBody(obj)`, `impulse(obj, vx, vy, vz)`, `bodyOf(obj)`; `physicsState()` lists the bodies. A `sphere` body rolls: its mesh turns with the ground speed (0.4.0). `spring(obj, { anchor, k, damping, rest })` hangs a body on a spring from an anchor (0.5.0), `unspring(obj)` frees it. `hinge(obj, { pivot, length, axis, angle, damping })` hangs an object from a pivot as a pendulum that swings under gravity and settles (a sign on a bracket, a lamp on a chain); `swing(obj, omega)` pushes it, `removeHinge(obj)` takes it off. The step is semi-implicit Euler at 50 Hz with separation along the smallest overlap of axis-aligned boxes, enough for crates that fall, stack and slide; `CO.physicsSolver = { step(bodies, dt, PHYS) }` plugs a full solver in with the same body list; `GAME.physics = false` switches the pass off. The editor's Drop (the inspector, or the `drop` tool) lets a placed prop fall from a little height and writes where it rests into the layout, as an undo step.

## 6i. Tuning tables (0.5.0)

`CO.table(name, obj, desc)` registers a live table a game tunes by (the faults and what each pays, the economy, the ladder); `CO.tune({ name: { 'path.to.leaf': value } })` holds overrides and applies them the moment the table registers, so the editor's `src/00-tables.js`, which runs first, wins over the code. The bridge lists every number, string and boolean leaf by path with its code value (`tables()`), sets one live as an undo step (`tableSet(name, path, value)`), and writes the part (`tablesCode()`). The editor's Settings tab edits them.

## 6j. The road network (0.11.0)

Lanes are directed polylines of `[x, z]` points. A road piece adds its own from its build with `c.lane(points, opt)`, in the piece's own coordinates, so they move and turn with it; a game adds one in world space with `roadLane(points, opt)` (opt.y is its height). Lane ends that meet, within 1.2 m and heading within 60 degrees, join into one network, rebuilt within half a second of a piece being placed, moved or removed.

`roadTraffic({ cars, speed, colours })` keeps that many cars on the network (`roadTraffic(0)` takes them off). The cars sit in `traffic.cars` beside the lane cars of `trafficAdd`, flagged `road: true`, so the editor lists them as before. Their rules:

- At a lane end a car takes one of the lanes that follow at random. A lane end that leads nowhere sends it back to a lane nothing feeds, so a straight road with open ends behaves like the old wrapping lanes.
- It keeps its distance to the car ahead on its lane and the next one, and to any car close in front in its path. When two cars each have the other in front, only one waits (the lower priority lane, then the later car), so they cannot lock each other.
- Lanes with the same `opt.box` are a junction: a car goes in only when no car from another approach (`opt.from`) is inside or has reserved it, and only with room on the far side, so nobody stops in the box.
- `opt.prio` marks a lane with priority, such as a roundabout's ring. A loop of priority lanes takes one car per 10 m; a car waits at the line to join a full one. A lane with `opt.merge` (a roundabout entry) gives way at its start to anyone coming round within 22 m, and once on it the car carries on.
- `opt.r` is a lane's curve radius; a car slows to suit it, and slows ahead of a tight lane it is about to take.
- A car held at a line for 9 s goes anyway, except into a busy junction or a full loop.

The road pack's pieces drive on the right, 1.75 m off the centre line. The straights carry a lane each way. The crossroads carries straight on, right and left from every arm, and the T-junction the turns its three arms allow. The bend carries one lane each way, the roundabout a one-lane ring with an entry and an exit on each arm, and the dead end a lane round its turning circle. The dev command `lanes` (or `lanes on`, `lanes off`) draws the network: blue lanes, amber priority lanes and red lane ends that lead nowhere.

## 6k. The menu maker (0.12.0)

`CO.menus({ theme, start, pause, settings, pages })` describes the start screen, the pause menu, the settings and the text pages a button opens; the engine draws them into the page's `dc-start` and `dc-menu` (part 46). A section left out keeps the page's own markup, so a game opts in a screen at a time. The editor's Menus tab edits it with the menu showing live in the viewport and writes `src/00-menus.js`; "Use the menu maker" starts from what the page has. A game made with New, and the template, start with one. When the editor saves a start screen it marks the page's `dc-start` with `data-co-menus` and keeps it hidden, so the page's own card does not flash up while the game loads; the engine shows it once the made one is drawn, or at once when no start screen is made.

- `theme`: `accent`, `panel`, `text`, `muted` colours, `font`, `radius`, `dim` (how dark behind), `align` (`center` or `left`), `width`, `layout` (`stack` or `row`) and `image`, the start screen's backdrop.
- `start`: `title`, `subtitle`, `logo`, `chips` and `note` (the save chips and the slot line, on by default), `keepPage` (on unless false: whatever else the page's start card held, a disclaimer or support links, stays under the buttons) and `buttons: [{ label, action, primary }]`. Its actions: `play`, `new` (this slot again, after a second click), `settings`, `guide`, `slots`, `quit` (closes the window in the desktop build) and `page <name>`.
- `pause`: `title`, `line` (the save line under it) and `buttons`. Its actions: `resume`, `settings`, `guide`, `stats`, `saves`, `edit`, `devlink`, `reset`, `quit` and `page <name>`.
- `settings`: `hide`, the engine settings to leave out (`sens`, `invertY`, `fov`, `bob`, `quality`, `sound`, `vol`, `film`, `fps`), and `custom: [{ key, label, type, min, max, step, options, value }]` with type `toggle`, `slider` or `select`. A custom setting lives in `SET` beside the engine's, is kept with them, reaches `GAME.setting(key, value)` and the `settings` hook when it changes, and `setting(key)` reads it.
- `pages: { name: { title, text } }`: text in paragraphs and `- ` lists.

Any other action is a dev command or code over the kit, as a UI panel button's is. The editor bridge has `menus`, `menusSet`, `menusSeed`, `menusPreview('start' | 'pause' | 'settings' | null)` and `menusCode`; the MCP server has `menus`, `menus_set` and `menus_preview`.

## 6l. The NPC creator (0.12.0)

`CO.npcs({ characters, spawners, workers, spots })` describes a game's people and what they do (part 47). The editor's NPCs tab edits it and writes `src/00-npcs.js`; "Use the NPC creator" lays out a customer who drives in, talks at a desk and leaves, and a clerk at a counter, where the camera looks.

- `characters: { id: { names, look: { shirt, pants, skin, hair, style }, speed, car, steps } }`. One of the names is picked for each NPC.
- `spawners: [{ id, character, x, z, every, max, hours: [from, to], park: [x, z], via, on }]` make a character every so many seconds, up to `max` at once, inside the hours (the game's `S.time`). A character that comes by car drives from `x, z` through `via` to `park` and gets out on the driver's side.
- `workers: [{ id, name, character, x, z, ry, home: [x, z], hours }]` keep a place: they walk in from home when their hours start (or stand there all along without hours), run their character's steps over and over, and go home when the hours end.
- `spots: { name: { x, z, ry } }` are the places a step walks to.

Steps run from the top. `walk { to }` goes to a spot's name, `x, z`, `player`, `home`, `car` or `post` (a worker's place), by the route finder where its grid reaches and straight where it does not. `say { text, wait }` puts up a speech bubble (`{name}` is the NPC's name). `talk { prompt, text, choices }` waits for the player to press E on the NPC and opens a panel; each choice has `label`, `say`, `run` and `then` (`next`, `stay`, `leave`, `repeat` or `step N`). `wait { seconds }`, `wander { radius, seconds }`, `face { to }`, `mood { mood }`, `until { test, every }` (an expression over the kit, with `npc`), `run { code }` (a dev command or code, with `npc`), `event { name }` (`runHooks('npc', name, npc)` and `GAME.npcEvent(name, npc)`), `leave`, `repeat` and `goto { step }`. A choice also tells the game, as the event `choice`.

The `npc` an expression or a command sees has `id`, `name`, `character`, `data` (its own store for the game), `x`, `z`, `step`, `say(text)`, `leave()`, `go(step)` and `next()`. NPCs are not saved: spawners and workers make them again from the data when the game loads. The editor bridge has `npcs`, `npcsSet`, `npcSpawn(spawner index, id or character)`, `npcInfo`, `npcAim`, `npcClear` and `npcsCode`; the MCP server has `npcs`, `npcs_set`, `npc_spawn` and `npc_info`.

## 6m. Keeping a game on the current engine (0.12.1)

When the editor opens a game it reads which engine the game runs: the tag an npm game pins in `package.json`, or `engine/VERSION` in a game made with New. Older than the editor's own, a bar over the viewport says so; its Update button runs `npm install co-engine@<repo>#v<editor version>` and the game's build (or copies the engine's parts in, for a game made with New) and restarts it. What changes is `package.json`, `package-lock.json` and `game/`, ready to commit. The editor's **menu first** option opens a game at its start screen (`CO.editor.atMenu()`) instead of entering it.

## 7. The editor bridge

Since 0.1.5 the page carries `CO.editor` (`engine/60-editor.js`), published as `window.CO_EDITOR` and switched on by `?editor=1` in the page's query (the editor's viewport loads the page with `?dev=1&editor=1`). It is the one surface the editor, the MCP server and a test talk to:

- `tree()`: what stands in the scene, by category (props by catalogue group, lights, people, doors, screens, vehicles, other), with counts, the time, the selection, the pause and scene-camera flags. Every object gets a stable id (`e<n>` stamped in `userData.eid`; a placed prop's id is its layout key).
- `inspect(id)`: the transform, material, geometry, light, screen and prop fields (type, label, category, x, z, turn, height, hidden, moved, solids) of one thing; `set(id, path, value)` edits them (`prop.x`, `prop.z`, `prop.rot`, `prop.h`, `prop.hidden`, `prop.reset` go through the layout and the save; `position.*`, `rotation.*` in degrees, `scale.*`, `visible`, `material.color`, `material.emissive`, any numeric material or light field, `name` edit the live object).
- `select(id)` draws the selection box, `pick(nx, ny)` raycasts a viewport point (baked merges, helpers, hit volumes and hidden things skipped), `frame(id)` flies the scene camera to a thing, `spawn(type, x, z)` places a copy ahead of the camera, `remove(id)` takes a placed prop out.
- `mode('scene' | 'game')` is the engine's photo camera on or off; `pause(v)` and `step()` drive `CO.paused` and `CO.stepOnce`; `enter()` starts the game from its menu (`GAME.editorEnter` when the game's own menu needs a click, else the engine's `enter`); `command(line)` runs a dev command; `assets()` lists the prop definitions, materials, textures, sounds, people presets and catalogue groups; `shot(q)` returns the viewport as a JPEG data URL; `sfx(name)` plays a sound.
- In the viewport there is no pointer lock (a locked pointer in an embedded page brings Electron down): a left click picks and selects, and the look follows the mouse while the right button is held, in the scene camera and in the game alike. The game reports a selection with a `console.log('[co-editor] {...}')` line that the editor catches. Since 0.4.0, in the scene camera, dragging the selected prop with the left button moves it over the ground (snapped to 0.05 m, 0.5 with Shift) and commits one `move` undo step on release; with the Model tab open the left button picks and drags a part of the modelled prop the same way. `set(id, 'prop.xz', [x, z])` moves both at once. Since 0.5.0, Ctrl and the left button grab whatever prop is under the pointer and drag it, in the game view as well as the scene camera, and Ctrl and the wheel turn it a quarter at a time; a wall prop dragged near a wall snaps onto it and turns to face out; `mode('top')` looks straight down. Terrain strokes, material and UI edits are undo steps too. A game that builds its props itself names its builder in `GAME.buildProp(id)` and the bridge rebuilds through it (Grow Co does).
- A game extends the tree and the inspector with `GAME.editorTree(eid)` (extra categories) and `GAME.editorInspect(obj)` (a `game` group of fields), and names its menu's start with `GAME.editorEnter()`.
- **Undo and redo** (0.1.7): every edit the bridge makes is a step on a stack, `undo()`, `redo()`, `history()`: a prop field as a layout snapshot before and after, a live field as its old and new value (`get(id, path)` reads one), a spawn, a remove. Ctrl+Z and Ctrl+Y work in the viewport and in the editor. The game's own build mode is play, not editing, and is not on the stack.
- **Pack authoring** (0.1.7): `source(type)` gives a prop definition's build function as text, its fields, its placed instances and the kit; `preview(type, code)` compiles a new build function and rebuilds every placed copy at once (a build that throws is refused and the previous one stays); `revert(type)` puts the original back; `define(code)` runs a whole `defProp(...)` live (a placed one builds at once, an extra joins the assets, a known id is redefined in place); `adopt(type)` makes a previewed build the baseline after it was saved. Since 0.6.0 the code runs inside the engine's own scope (a direct eval in the bridge), so it sees every name a part of the game sees; `kit()` still lists the common names (THREE, MAT, TEX, S, SET, box, cyl, sign, tex, textTex, std, glowMat, clamp, lerp, uid, floorY, propWorld and the rest of the engine's helpers), and a game adds its own with `GAME.editorKit` (an object, or a function returning one). The editor writes the saved function back into the `src/` part that holds it, and appends a new definition to the part with the most `defProp` calls.
- **The profiler** (0.1.7): `profile(true)` starts sampling, `profile()` reports fps, the frame's phases (sim, world, present, ui, render) in ms as averages and the last 120 frames, p95 and max, draws and triangles of the scene pass, programs, geometries, textures, the heap, and the counts (props, baked meshes and their draws, dynamic, interactive, solids, animated, lights against the budget); `profile(false)` stops it and drops the samples. The frame marks its phases only while sampling is on.
- **Saved into src** (0.1.8): the editor writes `src/00-layout.js` a moment after every move, hide, spawn or remove (its tree refresh compares `layout().code` with what it last wrote), the Pack tab writes build functions back where they live, and Ctrl+S (`save`) does both at once. **Release** (0.1.8): from the Build menu or the `release` tool, with a version, a title and notes: `package.json` and the lock take the version, `CHANGELOG.md` gets the entry on top, the game builds and checks (and builds the installer onto the Desktop when asked), everything is committed as `Release vX.Y.Z`, pushed, and the GitHub release is created with the notes (through `gh` when it is on the PATH, else by pushing the tag), after which the repo's Release workflow attaches the installer. `release_preflight` tells what would happen first.
- The same bridge is what the editor's MCP server (`editor/mcp.js`) exposes to Claude Code, tool by tool (status, scene_tree, inspect, set, select, frame, spawn, remove, camera, pause, step, command, assets, screenshot, console_log, plus run_js (code inside the game's scope, for playtests), undo, redo, history, prop_source, prop_preview, prop_revert, prop_define, pack_save, profile, layout_save, save, release_preflight, release, terrain, terrain_new, terrain_brush, terrain_scatter, terrain_off, materials, material_set, material_remove, material_shot, packs, pack_add, clips, clip_set, clip_play, clip_stop, clip_key, clip_remove, ui, ui_set, ui_open, model_get, model_set, model_save, physics, body_add, body_remove, impulse, drop, and open_game, play, reload, build, check, test, run_script on the editor itself). A game folder's `.mcp.json` names it; the template carries one.

## 8. The test handle

`window.<handle>.T` carries the engine's part (`S`, `player`, `ui`, `edit`, `run(sec)`, `setTime`, `lookAt`, the props, doors, screens, panels, menu, cards, photo, dev link, people, vehicles, weather, bake and helpers; see `coHandle` in `engine/90-boot.js`) merged with `GAME.T`. The smoke runner (`tools/smoke-runner.js`) wraps a scenario body with `T`, a live `S`, `ok`, `info`, `near` and `wait`, and fails the run on any page error.
